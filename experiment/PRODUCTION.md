# 本番化 — デプロイ手順

乙課題(較正)と frac課題(本計測)の6本を、クラウドソーシング(Yahoo!クラウドソーシング等)で
実施できる本番仕様にした。`?prod=1` を付けたときだけ「本番モード」になり、
同意画面・各試行のサーバ保存・完了コードが有効になる。
`?prod` が無ければ従来どおり研究者パイロット(ローカルDL)として動く。

## 本番URL(デプロイ後)

乙課題(較正・干渉ゲート)

- 聴覚乙: `.../experiment/pilot_soa_audio.html?prod=1&wid=<作業者ID>`
- 視覚乙: `.../experiment/pilot_soa_visual2.html?prod=1&wid=<作業者ID>`

frac課題(本計測)

- 聴覚1文字: `.../experiment/audio1char.html?prod=1&wid=<作業者ID>`
- 聴覚2文字: `.../experiment/audio2char.html?prod=1&wid=<作業者ID>`
- 視覚1文字: `.../experiment/visual1char.html?prod=1&wid=<作業者ID>`
- 視覚2文字: `.../experiment/visual2char.html?prod=1&wid=<作業者ID>`

`wid`(または `worker_id`)は各プラットフォームが受け渡す作業者IDのパラメータに合わせる。
点検モード(`?check=1`)や候補プール(`?pool=`)は本番モードと排他(点検が優先。聴覚乙のみ)。

## セットアップ(一度だけ)

1. **Googleスプレッドシートを作る**。URLからシートIDを控える。
2. スプレッドシートの「拡張機能 → Apps Script」に `gas/code.gs` を貼る。
3. 「プロジェクトの設定 → スクリプト プロパティ」に登録:
   - `SPREADSHEET_ID` = 上のシートID
   - `ANSWER_KEY` = `experiment/answer_key_merged.json` の全文
     (乙課題は正答をクライアントが送るため必須ではないが、frac課題の採点には必須)
4. 「デプロイ → 新しいデプロイ → ウェブアプリ」:
   - 実行者: 自分 / アクセスできるユーザー: 全員
   - 発行された `/exec` URL を控える。
5. `experiment/prod_common.js` の `const SUBMIT_URL = ""` にその `/exec` URL を貼る。
   (空のままだと本番モードの画面は出るが送信はスキップする。ローカル確認用。)
   送信先は6本すべてでここに一本化してある。各課題のJSに送信先は無い。
6. コミットして GitHub Pages に反映。

## 保存されるデータ

シートのヘッダ行は、GAS がシートを**新規作成するときだけ**書き込む。
すでに `trials` / `soa_trials` / `soa_sessions` があるシートに対しては列が増えても
ヘッダは更新されないので、**列を追加した今回は、新しいシートで始めるか、
ヘッダ行を手で追記すること**。

- `soa_trials` シート(乙課題): 1試行1行。
  `ts, participant_id, worker_id, completion_code, task, trial_index, version, speaker, pitch,
  S, c1, c2, c3, resp1, resp2, correct1, correct2,`
  **`actual_soa1, actual_soa2, actual_dur3, ua, dpr, screen, touch, refresh_hz`**(今回追加)
- `soa_sessions` シート(乙課題): セッション完了1行。従来の集計値に加えて
  **`ua, dpr, screen, touch, refresh_hz`**(今回追加)。
- `trials` シート(frac課題): 1試行1行。従来の列に加えて
  **`actual_ms, actual_frames, ua, dpr, screen, touch, refresh_hz`**(今回追加)。

### 追加した列の意味

- `actual_soa1 / actual_soa2 / actual_dur3`(視覚乙課題): requestAnimationFrame の実時刻から
  測った、実際の文字の間隔と3文字目の表示時間。名目値 S との差を見るためのもの。
  聴覚乙課題では空欄(Web Audio がサンプル精度で鳴らすため)。
- `actual_ms / actual_frames`(視覚frac課題): 名目の提示時間は `CHAR_MS * frac / 100` だが、
  実際には画面のリフレッシュ周期に量子化される。ターゲット文字を最初に描画したフレームから
  消去したフレームまでの実時間と、実際に描画したフレーム数を記録する。
  frac=0 の試行は一度も描画しないので 0ms・0フレームになる。聴覚frac課題では空欄。
- `ua / dpr / screen / touch / refresh_hz`: 端末環境。各ページが測って
  `PROD.setEnv()` で登録し、`prod_common.js` が送信本文に自動で載せる。
  `refresh_hz` は読み込み直後に40フレームぶん測った推定値。
- `rt_ms`(frac課題): 「刺激の提示が始まってから回答するまで」の時間。
  クリック開始(自己ペース)にしたため、開始ボタンを押すまでの待ち時間は含まない。

## frac課題に入れた「乙式改善」(2026-08)

乙課題で先に導入した参加者体験を、frac課題4本にも移した。

1. **クリック開始(自己ペース)**: 刺激は自動で始まらない。
   「準備ができたら開始（またはスペースキー）」を押してから提示・再生する。
   押すまで50音の回答ボタンは押せない(提示前に答えてしまうのを防ぐため)。
   押したあとは同じボタンが「もう一度みる／きく」に変わり、従来どおり何度でも見直せる。
2. **教示と練習のフィードバック**: 何を答えるのか・**難しくて当然**であること・
   **勘で答えてよい**ことを、教示と練習の各問のあとの画面で繰り返し伝える。
   視覚課題は練習で正解も表示する。聴覚課題は正解表(answer_key)が端末に無いため
   正解は表示できず、参加者自身の答えと注意書きだけを見せる。
3. **出題の配り方**: 水準ごとに均等な試行数を割り当ててから順序を混ぜる方式にした。
   総試行数は従来どおり各課題 200 問(練習5問は別)。
   - frac 水準: 統制試行(frac=100)を 5%(10問)確保し、残り190問を21水準に均等配分(各9〜10問)。
   - 文字: 視覚課題は78字を均等配分(各2〜3回)。聴覚1文字課題は刺激プールが68音1対1なので
     刺激を均等配分すれば音も均等になる。
     **聴覚2文字課題だけは文字の均等配分ができない**(manifest に正解を含めない設計のため、
     クライアントがどの文字か知らない)。刺激は5184対からの非復元抽出のまま。
   - 提示アルゴリズム(視覚): fade・blur・moya を均等配分。

## 未確定(統括判断が要る。実装はこの配管に定数を差し込むだけ)

- **セッション設計と予算**: 1人あたりの試行数(乙課題は各水準6問=42問、frac課題は各200問)、
  必要人数、10万円枠での配分。→ 実験計画として別途決定。
- **干渉判定の事前登録ルール**: S=200 vs 頭打ち(450/700)の閾値・信頼区間・必要N。
- **frac課題1本あたりの所要時間**: 同意画面には「約20分」と書いてあるが、
  クリック開始にしたぶん自己ペースの待ち時間が加わる。実測して文面を調整するとよい。
