# 相談：RQ4（速さの影響）が、薄い水準では測れないことについて

**2026-08-25 作成。前提知識なしで読めるよう自己完結で書いてある。**
先に相談した `project/相談_視覚水準とフレーム量子化.md` の続きだが、**この文書だけで読める**。

---

## 1. 実験の全体像（30秒）

**音声を途中で打ち切って「何ミリ秒聞けば何%の人が字を当てられるか」という曲線 A(t) を測り、
その曲線と同じ形になるように文字アニメーションの進み方を計算で設計する。**
できたアニメを別の参加者に見せて、本当に同じ曲線が出るかを検証する。

日本語のひらがな1文字が題材。クラウドソーシングで428人を4集団に分けて実施。締切 2026-08-31。

1. **A(t)** … 音を t ms で打ち切ったときの正答率（群Acal・80人）
2. **V(s)** … 文字アニメを進み具合 s で止めたときの正答率（群A′・150人）
3. **s(t) = V⁻¹(A(t))** を計算してアニメの進み方の表を作る
4. その表で動くアニメを別集団に見せ、A(t) が再現されるか検証（群B・168人）

**視覚の提示方式は4通り**あり、方式ごとに V(s) を測る。

| 方式 | 進み具合 s が意味するもの |
|---|---|
| うすい→濃い（fade） | 字全体の濃さ（不透明度） |
| 点が増える（reveal） | 墨の画素のうち出す割合 |
| ぼやけ→はっきり（blur） | ぼかし半径 ＝ 72×(1−s) px |
| 端から現れる（wipe） | 字の幅のうち出す割合 |

---

## 2. RQ4 とは

**RQ4（探索的）**: 識別できるかは**進み具合だけで決まるのか、そこへ着くまでの速さにも左右されるのか**。

測り方: 群A′で、**基準アニメの長さを 300ms と 500ms の2通り**出す
（`base_anim_ms`。0→100% にかかる時間）。同じ進み具合 s に、**速く着いた場合と
遅く着いた場合**で正答率が変わるかを見る。

**位置づけ**: RQ4 は**探索**であり、確認的な検定（4本・Holm法で調整）には入っていない。
確認的検定は「うすい→濃い」「点が増える」の2方式 × 仮説1・2 の4本のみ。

**なぜ重要か**: 生成した s(t) は「進み具合の時間変化」でしかない。もし速さも効くなら、
V(s) という1変数の関数で転写する枠組み自体に限界があることになる。
だから RQ4 の答えは、この研究の前提の妥当性に関わる。

## 3. 今日わかったこと（実装の問題を直した結果、副作用が出た）

### 3.1 提示の仕組みを直した

もともとの実装は「進み具合が目標 s を超えたフレームは1枚も描かない」だった。
進み具合は **s = 経過ms ÷ base_anim_ms** の等速で決まるので、
**画面の書き換え周期（60Hzで16.7ms）より短い s は一度も表示されない**。
実測で「1.75% / 4% / 6.25% を指定した15問のうち11問が真っ白」になっていた。

そこで **「狙った s ちょうどにクランプして1枚描き、固定時間だけ残してから消す」** に変えた。

- 保持は **フレーム数**で数える（`endpoint_hold_ms = 34` を端末のリフレッシュレートで
  割った枚数。30Hz 1枚・60Hz 2枚・90Hz 3枚・120Hz 4枚）
- ⚠ **一度「34ms 待ってから消す」にしたが、それでは揃わなかった。**
  白紙が実際に画面へ出るのは次の repaint なので、実表示時間は
  30Hz 約67ms・60Hz 約50ms・120Hz 約42ms とばらつく。
  フレーム数で数えると **30〜120Hz で 33.3ms にそろう**（144Hz で34.7ms）
- 「描いたのに一度も画面に出ない」（負荷が高いとき・進み具合2%で表面化）も防げる

**この変更で RQ4 の交絡が1つ解けた。** 旧実装では2つの速さで最終状態がずれていた:

| 狙い | 300ms の最終s | 500ms の最終s |
|---|---|---|
| 6% | 5.6% | **3.3%** |
| 50% | 44.4% | **46.7%** |

速さを変えると**最終状態まで変わっていた**ので、「速さの効果」と「状態の違い」が
分離できていなかった。いまは両方とも狙いどおりの s で揃う。

### 3.2 水準を方式ごとに分けた

4方式は同じ進み具合でも難しさが桁違いで（実測で、同じ 1.75% でぼかしだけ 4/4 正解・
他の3方式は全滅）、1つの並びを共用すると、ある方式では8水準のうち6つが床、
別の方式では6つが天井になり**その方式の曲線が描けない**。そこで方式ごとに並びを持たせた。

| 方式 | 水準% |
|---|---|
| うすい→濃い | 0.4, 0.8, 1.4, 2.2, 3.5, 6, 12, 100 |
| 点が増える | 0.1, 0.25, 0.5, 1, 2, 4, 9, 100 |
| ぼやけ→はっきり | 10, 18, 26, 34, 42, 52, 65, 100 |
| 端から現れる | 0.5, 1, 2, 4, 8, 14, 25, 100 |

**個数は8にそろえてある**ので、1人あたりの問題数（70問）もセルの数も変わらない。

薄い側の水準がこれほど低いのは、**34ms 保持にしたことで以前（1フレーム＝17ms）より
見やすくなり、4方式とも薄い側へ置き直す必要が出た**ためである。
物理的な下限は、うすい→濃い 0.4%（濃さが256段階しかない）、
端から現れる 0.5%（幅が1画素）、点が増える 0.01%（点が1個）。

## 4. 相談したい問題

**薄い水準では、2つの速さの差が画面に出せない。**

「うすい→濃い」の例（基準アニメ 300ms と 500ms）:

⚠ **この節は 2026-08-25 に書き直した。最初の版は「到達時刻の差が1フレーム未満なら
同一刺激」と書いていたが、これは誤りだった。** 登っている途中も**毎フレーム中間状態を
描いている**（`renderer.draw(ctx, char, s)`）ので、到達時刻が近くても
**中間フレームの枚数や中身が違えば別の刺激**になる。以下は訂正後の内容。

実際に描かれる絵の並び（うすい→濃い・60Hz）:

| 水準 | 300ms で描かれる s | 500ms で描かれる s | |
|---|---|---|---|
| 0.4% | 0 → 0.4 | 0 → 0.4 | **完全に同一** |
| 2.2% | 0 → 2.2 | 0 → 2.2 | **完全に同一** |
| 3.5% | 0 → 3.5 | 0 → **3.33** → 3.5 | 中間が1枚多い |
| 6% | 0 → 5.56 → 6.0 | 0 → **3.33** → 6.0 | 中間の中身が違う |
| 12% | 0 → 5.56 → 11.11 → 12.0 | 0 → 3.33 → 6.67 → 10.0 → 12.0 | 明確に違う |

**同一になる条件**は「**遅いほう（500ms）も最初の非ゼロフレームより前に到達する**」で、
60Hz なら **3.33% 以下**。しかも**端末で変わる**（120Hz なら 1.67% 以下、30Hz なら 6.67% 以下）。

したがって3つの領域がある。

| 領域 | 60Hzでの水準 | 内容 |
|---|---|---|
| **完全に同一** | ≤ 3.33% | 両方とも [0 → 目標] の2枚だけ |
| **弱く違う** | 3.5〜6% | 中間フレームの枚数・中身だけが違う |
| **強く違う** | 12% 〜 | 到達時刻が1フレーム以上ずれる |

⚠ **この分類は理屈の表で決め打ちできない**（端末のリフレッシュレートに依存するため）。
**記録から事後に分類する**のが正しい。`actual_frames` が **2枚**（s=0 の初期描画＋
クランプの1枚）なら中間フレーム無し＝同一刺激、と機械的に判定できる。
`refresh_hz` も試行ごとに記録済み。

参考までに、到達時刻の差だけを見た表（**同一性の基準ではない**）:

| 水準 | 300ms | 500ms | 差 |
|---|---|---|---|
| 0.4% | 1.2ms | 2.0ms | 0.8ms |
| 3.5% | 10.5ms | 17.5ms | 7.0ms |
| 12% | 36.0ms | 60.0ms | 24.0ms |
| 100% | 300.0ms | 500.0ms | 200.0ms |

**これは 34ms 保持のせいではない。** 34ms は両方の速さに同じだけ足されるので
差の向きを歪めない（交絡にはならない）。原因は、**薄い水準では「登る時間」そのものが
極小**であることにある。34ms をやめても、1フレーム未満の差は出せない。

補足として、全体の提示時間で見ると 34ms 保持が**相対的なコントラストを薄める**効果はある:

| 水準 | 全体(300ms) | 全体(500ms) | 比 |
|---|---|---|---|
| 0.4% | 35ms | 36ms | 1.02 |
| 12% | 70ms | 94ms | 1.34 |
| 100% | 334ms | 534ms | 1.60 |

（登る時間だけなら比は常に 1.67。34ms が定数で入るぶん比が縮む。）

## 5. 考えた選択肢

### 案1: このまま。測れる範囲で測り、測れない範囲は明記する

RQ4 は探索なので、**主に「ぼやけ→はっきり」で答える**（唯一8水準すべてで速さが効く）。
他の3方式は濃い側の2〜3点で補助的に見る。
論文には「速さの効果は、進み具合が十分大きい領域でのみ検証可能」と書く。

### 案2: 速さ2水準を「ぼやけ→はっきり」だけにする

設定で方式を絞れる（`calib_speed_probe.families`）。薄い側の3方式では速さを1つに固定し、
浮いた問題数を他に回す。
ただし **「速さの影響は方式によって違うか」という問いが測れなくなる**
（2026-08-24 に、まさにそれを見るために速さ2水準を1方式から4方式へ広げた経緯がある）。

### 案3: 基準アニメを長くする（600msに戻す）

差が広がる。ただし 600→300 にしたのは **群Bの対照条件（等速表示）が構造的に不利**
だったためで、戻すとそちらが壊れる。
（300msなら音の打ち切り220msの時点で進み具合73%まで進むが、600msだと37%までしか
進まず、「どの時刻でも字が薄すぎて読めない」状態で提案手法と比べることになる。）
較正と生成で速さを揃える必要もあるので、群A′だけ長くすることもできない。

## 6. 相談したいこと

1. **案1・2・3 のどれが妥当か。** 1つ選んで理由を書いてほしい
2. **そもそもこれは「問題」なのか。** 「薄い水準では登る時間が1フレーム未満なので
   速さの効果は原理的に存在しない」と考えれば、測れないのではなく
   **測るべきものが無い**とも言える。この整理は正しいか
3. **RQ4 の問いの立て方を変えるべきか。** いまは「同じ s に速く着いたか遅く着いたか」
   だが、薄い水準では「着くまでの時間」がほぼゼロなので、問いが意味を持つのは
   ある程度濃い領域だけ、ということになる。問いの範囲を最初から限定して
   事前登録し直すべきか
4. **見落としている選択肢**があれば指摘してほしい（案1〜3以外の第4の道）
5. **34ms 保持そのものへの評価。** 交絡は生まないが相対コントラストは縮む。
   保持時間を速さに比例させる（300msなら34ms・500msなら57ms）案も考えたが、
   それだと**最終画像の露出時間が速さで変わる**という別の交絡が入ると判断して
   採らなかった。この判断は妥当か
