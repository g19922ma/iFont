# 補償タスク（常設・使い回す）

> **決定（2026-08-27）**: 補償用のタスクを1本だけ立て、**以後の課題すべてで使い回す**。
> タスク作成の手数料（1000〜2000円）は1人分の補償に対しては割高だが、
> 一度立てれば実験2・実験3で同じことが起きても追加費用なしで対応できる。

## 仕組み

**タスク一覧に表示しない**設定にし、**キーワード**で対象者を絞る。

**ホワイトリストは使わない。** 掲載後に途中で変更できないため、
対象者が増えるたびに登録し直すことができず、常設のタスクには向かない。
**この設計はホワイトリストに依存していない**（下記のとおり、本当の門は会員IDである）。

- 一覧に出ないので、URL を知らせた人以外はまず辿り着かない
- コード（12桁の数字）は個別メールでのみ伝える。**タスクの設問も兼ねる**
- **守っているのは承認の運用そのもの**。URL を知れば誰でもエントリーはできるが、
  キーワードが合っていない回答は**承認しない**（＝支払わない）

⚠ **手作業での承認はできない。キーワードが自動判定の門そのものになる。**

当初は「会員IDを見て承認する」つもりだったが、**手動承認の仕組みが使えない**ことが
分かった（2026-08-27）。正しいキーワードを入れた人には自動で支払われるため、
会員IDで弾くことはできない。

**被害の上限は「50枠 × 報酬額」で頭打ちになる。**
報酬が50円なら最大2,500円、15円なら750円で、タスクの手数料と同水準かそれ以下。
青天井ではないので、この方式で運用してみる。

露出を減らす工夫（できる範囲で）:
1. **一覧に出さない。** URL を知らせた人以外はまず辿り着かない
2. **必要なときだけ開ける。** タスクを停止できるなら、普段は止めておき、
   対象者に連絡するときだけ開け、受け取りを確認したら止める
   （※停止と再開ができるかは未確認。できるなら最も効く）
3. **キーワードは掲載後に変えられない**（設問文を編集できないため）。1つ固定で運用する

### コードは2つ作る（丸山さん案・2026-08-27）

⚠ **丸数字（①②）は使わない。** 機種依存文字（cp932 の NEC 拡張領域）のため、
   厳密な Shift_JIS で読む相手には `invalid encoding` で弾かれる。
   2026-08-27 に実際にアップロードが失敗した。**A / B のような半角英字を使うこと**（1 / 2 はコード本体の数字と紛らわしい）。
   ほかに ⅠⅡ ㈱ № ℡ なども同じ理由で避ける。

| | 値 | 役割 |
|---|---|---|
| **コードA** | `115408162144` | 本命の設問で聞く。**支払いの判定には使われない**（記録として残るだけ） |
| **コードB** | `114516088688` | **チェック設問の答え。これが支払いの自動判定に使われる** |

なぜ2つ要るか。テンプレートは**チェック設問だけの構成を受け付けない**（calib2 のときに
「設問0問」で弾かれた）。本命の設問が最低1つ要るので、そこでコードAを聞き、
チェック設問でコードBを聞いて判定する。参加者から見れば「2つのコードを入力する」だけである。

⚠ 数字にしたのは推測されにくいからではなく、**入力ミスが起きないから**である。
   ひらがなはスマホのIMEで打ち間違えやすく、打ち間違えると支払われず
   「また受け取れなかった」という次の苦情になる。コピペできる数字ならその事故がない。

⚠ 漏えい対策としては効果がない。丸ごとコピーされれば桁数は関係ない。
   守っているのは「一覧に出さない」ことだけである。

⚠ **掲載後は変更できない**（設問文を編集できないため）。決めてから掲載する。

### 設問データTSVと掲載設定（確定・2026-08-27）

`project/設問データ_ポイント受け取り用タスク_0827.tsv`（cp932・CRLF・7列・12行）
- ヘッダ 1行
- **本命 1行**（設問ID `1`、チェック無し、コードAを聞く）
- チェック 10行（chk01〜chk10、チェック有り、答えはコードB）

| 掲載設定 | 値 |
|---|---|
| 設問数 | **1問** |
| 1タスクあたりの設問数 | **2問（内チェック設問 1問）** |
| タスクの重複出題回数 | **19回** |
| タスク一覧への表示 | しない |

⚠ **タスクの種類は「データチェック」を選ぶ。「アンケート」では通らない**（2026-08-27 に判明）。
   この 7列テンプレート（F03:テキストエリア＋チェック設問の解答）は
   データチェック用である。アンケートを選ぶとアップロードできない。

⚠ **設問数とTSVの本命行数は一致させること。** 設問数1に対して本命が50行あると
   噛み合わない（最初 50行で作って作り直した）。

**枠は「設問数 × 重複回数 = 1 × 19 = 19人分」**になる。
コードが漏れた場合の被害の上限も 19 × 報酬額 で頭打ちである。

⚠ ホワイトリストも掲載後に変更できないため使わない。
   1回きりなら使えるが、常設で使い回す方針と両立しない。

⚠ **重複回答は「1回」に設定する。** そうしないと1人が複数の枠を取れてしまう。

⚠ 説明文は **URL を知れば誰でも読める**ものとして書く。
   個別の事情や不具合の断定は書かない。

⚠ **一覧への表示はオフのままにする。** 一覧に出ると無関係な作業者が
   次々エントリーしてキーワードを外し、大量の非承認を出すことになる。
   非承認は作業者側に不満が残り、50枠が一時的に埋まって対象者が入れなくなる恐れもある。
   やむを得ず一覧に出す場合は、説明文の「ご連絡を差し上げていない方は対象外」を
   **冒頭に置く**こと。

⚠ 「不備」「補償」「お詫び」を名前に入れない。運営から見ると事故報告に見える。

### 書き方の方針

- **原因に触れない。** 記録から特定できておらず、調査状況は相手の関心事でもない。
  書くほど言い訳がましくなる。聞かれたらそのとき答える（詳しくは末尾の参考）
- **説明しすぎない。** 「お客様に落ち度はございません」等は補償を出す時点で伝わる
- 相手が聞いてきたこと（今後も掲載するか／補償はあるか）には必ず答える
- **「また同じ課題をやってください」と誘わない。** 環境に対応できていなかった可能性がある以上、
  同じものを勧めるのは筋が通らない
- **「ご安心ください」と書かない。** 相手が心配していた前提になる。
  **個別に対応するという事実だけ**を伝える

## 対象者の見つけ方（実験2・実験3でも同じ）

補償の対象は「実施したのにポイントを得られなかった人」である。次の2つを突き合わせる。

1. **Yahoo! の納品データ / 作業者一覧** … 会員IDと、キャンセル・時間切れの別が分かる
2. **こちらのサーバ記録**（`experiment/tools/build_approval_calib2.py` が作る承認判定CSV）
   … wid ごとに「開始したか」「完走したか」「回答数」が分かる

**「開始の記録はあるが回答が0件」の wid** が第一の候補である。
設問データTSVの wid と Yahoo! の会員IDは納品データで対応が取れるので、
そこから会員IDを引いて「対象者の記録」表に足す。

⚠ **キャンセルは対象にしない**（自発的な辞退のため）。時間切れと、
   申し出があった方を対象とする。

⚠ 会員IDの取り違えに注意する。数の一致だけで同定せず、
   納品データで wid と会員IDの対応を確認すること。

## 対象者が出たときの手順

1. 「対象者の記録」の表に、会員ID・事情・連絡日を書く
2. 個別メールで URL とキーワードを送る（キーワードは常に同じ）
3. 支払いはキーワードの一致で**自動的に行われる**（手動承認はできない）
4. 納品データで会員IDを確認し、表の「支払済」に印を付ける
5. 対象外の会員IDからの受け取りが見つかったら、キーワードが漏れた合図。
   枠が食われ続けるようなら、タスクを止めるか立て直す

## 参考：2026-08-27 の事例について（参加者には見せない）

原因は特定できていない。可能性は二つあり、記録からは区別できない。

1. **設計どおり、ほとんど見えない水準が続いた。**
   この方（連番161）に出るはずだった24問を再現すると、8問が正答率10%未満。
   とくに「つ」のぼやけは 3.7% → 7.4% → 4.5% と3問連続で何も見えない配置だった。
2. **提示が完了せず、回答ボタンが押せないまま進めなくなった。**
   コード上この経路は実在する（提示が終わるまでボタンは無効で、
   エラーも出ず、先へ進む手段もない）。

ただし 1 については、提示が終わると「表示された文字を回答して下さい。
分からない場合でも、最も近いと思う文字を選んでください。」という案内が出て
ボタンが押せるようになる仕組みがある。それでも1問も押していない点は
1 だけでは説明しきれない。

**公開の文面で「不具合を確認しました」と書かない理由**
- 事実として確認できていない
- この課題は**正常に動いていても「文字が表示されない」ように見える**。
  不具合として公表すると、正常に完了した162名にも「自分も壊れていたのか」と
  思わせ、今後の掲載でも「壊れている」という前提で見られる

**完走者側の状況**: 162名が本命24問を完走。11,377試行すべてで2コマ以上描画されており、
200ms以上のコマ抜けは3試行のみ。提示の仕組み自体は正常に動いていた。

**次の掲載までに直すこと**
- 提示が完了しない場合でも先へ進めるようにする（詰み経路を塞ぐ）
- 数秒たっても回答がない場合に「見えなくても選んでください」をはっきり出す
  （今は350ms後に小さくじわっと出るだけ）
