# 相談：視覚刺激の「進み具合」が画面のフレームに縛られる問題

**2026-08-25 作成。他のAI／人に相談するための自己完結の説明。**
前提知識なしで読めるように書いてある。

---

## 1. この実験は何をするものか

**音声を途中で打ち切って「何ミリ秒聞けば何%の人がその字を当てられるか」という曲線を測り、
その曲線と同じ形になるように文字アニメーションの進み方を計算で設計する。**
できたアニメーションを別の参加者に見せて、本当に同じ曲線が出るかを検証する。

日本語のひらがな1文字（全68字。うち測定対象は8字）が題材。
クラウドソーシングで428人を4集団に分けて実施予定。締切は 2026-08-31。

手順:

1. **A(t)** … 音を t ミリ秒で打ち切ったときの正答率曲線を測る（群Acal・80人）
2. **V(s)** … 文字アニメを進み具合 s で止めたときの正答率曲線を測る（群A′・150人）
3. **s(t) = V⁻¹(A(t))** を計算して、アニメの進み方の表を作る
4. その表で動くアニメを別の集団に見せ、A(t) が再現されるか確かめる（群B・168人）

**視覚の提示方式は4通り**ある（うすい→濃い／点が増える／ぼやけ→はっきり／端から現れる）。
方式ごとに V(s) を測る。

---

## 2. 視覚較正（群A′）の実装

文字が **0% → 100%** へ進むアニメを再生し、**指定した進み具合 s で止めて消す**。
その状態で「何の字だったか」を68字の表から選ばせる。

- アニメの長さ `base_anim_ms = 300ms`（0→100%にかかる時間）
- 進み具合は **s = 経過ミリ秒 ÷ 300ms** の等速
- 実装（requestAnimationFrame のループ）:

```js
function frame(now) {
  const el = now - tOn;            // 提示開始からの経過ms
  const s  = el / 300;             // 進み具合
  if (s >= sTarget) { 画面を白紙にして終了; return; }   // ← 描く前に判定
  renderer.draw(ctx, char, s);     // s の状態を1枚描く
  requestAnimationFrame(frame);
}
```

**要点: 目標 s を超えたフレームは1枚も描かない。** つまり
**「目標の s そのもの」は一度も画面に出ない。**
実際に見えた最大の進み具合は、目標より1フレームぶん手前になる。

なお提示開始の最初のフレームは `el = 0` なので **s=0 が必ず1枚描かれる**。

---

## 3. 何が問題か

### 3.1 フレームの間隔でしか刻めない

画面は一定周期でしか書き換わらない。60Hz なら 16.7ms ごと。
`base_anim_ms = 300ms` なので、**進み具合は 16.7/300 = 5.6% 刻みでしか止まれない**。

「3%」を指定すると 9ms で止めたいことになるが、最初の書き換えが 16.7ms なので
**s=0 の1枚（真っ白）だけが出て終わる**。

### 3.2 端末によって刻みが変わる

- 60Hz → 5.6% 刻み
- 120Hz → 2.8% 刻み
- **30Hz（ブラウザが重いとき）→ 11.1% 刻み**

同じ「6%」の指定が、端末や負荷によって「真っ白」だったり「5.6%が見える」だったりする。

### 3.3 実測（今日、開発者本人が本番URLで通した記録）

記録された `refresh_hz`: **60 が30件、31 が25件、77 が8件**。
実際のフレーム間隔は **約33ms（≒30Hz）** のことが多かった。

| 指定した水準 | 実際に起きたこと |
|---|---|
| 1.75% / 4% / 6.25% | **全部 s=0・1枚・33ms**（＝真っ白しか出ない） |
| 20% | あるときは **s=11.0%・2枚・67ms**、あるときは **s=13.4%・3枚・100ms** |
| 100% | **10枚**のときと **16枚**のとき |

**同じ指定でも回ごとに違う。** フレームが飛ぶ（60ms空くことがある）ため。

視覚の本命問題は25問で、**そのうち11問が s=0（真っ白）**だった。

### 3.4 方式によって「s=0」の意味が違う

**これが厄介な点。** s=0 のとき画面に出るものが方式で違う。

| 方式 | s=0 で出るもの | 今日の正答 |
|---|---|---|
| うすい→濃い | 濃さ0 ＝ **何も出ない** | 0/4 |
| 点が増える | 点0個 ＝ **何も出ない** | 0/4 |
| 端から現れる | 幅0 ＝ **何も出ない** | 0/3 |
| **ぼやけ→はっきり** | **最大ぼかしの字が1枚出る** | **4/4 正解** |

ぼかしだけ「s=0」で字が見えてしまうので、床（当て推量の水準）が取れない。
（対処として最大ぼかしを 24px → 72px に上げたが、それとは別の話として残る。）

## 4. 元の実験（v1）ではどう扱っていたか

同じ研究室の先行実験の計画書に、この問題が明記されている。

> 60Hz端末では1フレーム16.7msの量子化により低fracの水準が実効的に潰れ、初回フレームが
> 透明度0のため到達する濃さも名目より1フレームぶん低い。記録済みの actual_ms
> （および refreshHz から求まる実効到達透明度）を f(·) の入力とする。
> **名目fracはあくまで割付水準の記録とする。**

つまり **「提示の仕組みは直さない。解析では実測値を横軸に使う」** という方針だった。
いまの実装も1問ごとに `actual_s`（実際に見えた進み具合）・`actual_frames`・`actual_ms`・
`refresh_hz` を記録している。

**この方針は正しいが、それだけでは足りない**というのが今回の論点である。
実測値を使っても、**そもそも出せなかった値の点は作れない**。
今日のデータでは実際に出た値が **0 / 11.1 / 22.2 / …** しかなく、
**0 と 11.1 のあいだに点が1つも存在しない**。曲線の立ち上がりがそこにあると測れない。

---

## 5. これまでに分かっている曲線の位置

進み具合＝濃さ（当時 gamma=1.0）として、過去の実測。

**アニメ600ms・研究室の教員が通したパイロット（視覚163問）**

| 方式 | 濃さ2.5〜2.8% | 濃さ5.3〜5.9% | 12.5% | 100% |
|---|---|---|---|---|
| うすい→濃い | 3/7（43%） | **9/9（100%）** | 11/11 | 12/12 |

→ **600ms では立ち上がりが濃さ 2.8〜5.6% のあいだ**にある。

**アニメ300ms・今日（視覚25問・途中で中断）**

| 濃さ | 正答（ぼかしを除く3方式） |
|---|---|
| 0%（真っ白） | 0/11 |
| 11.0% | 1/2 |
| 13.4% | 1/1 |
| 100% | 4/4 |

→ 300ms（見る時間が半分）では立ち上がりがもっと濃い側にあるはずだが、
**0〜11% のあいだにデータが1つも無い**ので位置を特定できない。

## 6. 使える「つまみ」

**gamma**: 方式によっては「進み具合 → 実際の見え方」の対応を変えられる。
うすい→濃い では **濃さ = 進み具合^gamma**。

| 進み具合 | gamma=1.0 の濃さ | gamma=1.5 | gamma=2.0 |
|---|---|---|---|
| 5.6% | 5.56% | 1.33% | 0.31% |
| 11.1% | 11.1% | 3.70% | 1.23% |
| 22.2% | 22.2% | 10.5% | 4.93% |

**重要**: gamma を変えても科学的な結論は変わらない。
V(s) を測って V⁻¹ で逆引きする設計なので、**測るときと作るときに同じ gamma を使う限り、
合成 V(s(t)) = A(t) は不変**である。gamma は「進み具合」という物差しの目盛りの振り方にすぎない。

ただし **「出せる範囲」は変わる**。フレームの制約で進み具合の下限が決まっているとき、
gamma を上げれば同じ下限でもっと薄い絵を出せる。

**開発者本人が本番と同じ時間で再生して判定した結果**（答えの字を知っている状態なので、
「読めない」側にだけ強い結論が出る点に注意）:

- gamma=1.0（濃さ5.56%）→ **読めた**（＝床にならない）
- gamma=2.0（濃さ0.31%）→ **何も出なかった**（＝床にはなるが「無」）

## 7. 選択肢（ここが相談したいところ）

### 案A: 提示の仕組みを直す

打ち切りの規則を「目標 s を超えたら描かずに終わる」から
**「目標 s でちょうど1枚描いてから終わる」**に変える。

- **利点**: フレームレートに関係なく、指定した進み具合が必ず画面に出る。
  端末差・負荷の影響を受けない。水準を数値どおりに置ける
- **欠点**: v1の方針（提示は直さず実測で扱う）から外れる。
  提示**時間**のばらつきは残る（1フレームぶんが17msだったり33msだったり）
- 検証（群B）は「時刻 t 以降の情報を見せない」が正しいので**変えない**

### 案B: 現状のまま、実測値で解析する（v1の方針そのまま）

- **利点**: コードを変えない。先行実験と手続きが揃う
- **欠点**: 今日の実測では **25問中11問が真っ白**だった。
  低い水準の試行が軒並み同じ「s=0」に潰れ、
  **0〜11% のあいだを測る手段が無い**

### 案C: 水準を「フレームの粗い刻みの倍数のすぐ上」に置く

いちばん粗いのは 30Hz の 11.1% 刻み。**11.1% の倍数のすぐ上**を指定すると、
どの端末でも実際の値が揃うことを計算で確かめた。

| 指定 | 30Hz | 60Hz | 90Hz | 120Hz | 144Hz |
|---|---|---|---|---|---|
| 12% | 11.1% | 11.1% | 11.1% | 11.1% | 11.6% |
| 23% | 22.2% | 22.2% | 22.2% | 22.2% | 20.8% |
| 34% | 33.3% | 33.3% | 33.3% | 33.3% | 32.4% |
| 45% | 44.4% | 44.4% | 44.4% | 44.4% | 44.0% |
| 57% | 55.6% | 55.6% | 55.6% | 55.6% | 55.6% |
| 68% | 66.7% | 66.7% | 66.7% | 66.7% | 67.1% |

（33.3ms が 16.7 / 11.1 / 8.33ms の公倍数になっているため揃う。144Hz だけ少しずれる。）

- **利点**: コードを変えない。端末差の影響がほぼ消える。v1の方針とも矛盾しない
- **欠点**: **使える進み具合が 0 / 11.1 / 22.2 / … に限られる**。
  0 と 11.1 のあいだは相変わらず測れない。
  → ただし **gamma で「11.1% の見え方」を薄くできる**ので、
  11.1% を床にすることは可能（gamma=2 なら濃さ1.23%）
- 100% だけは注意（30Hz では 88.9% までしか届かない。ただし全部見せの条件は
  別処理で完成形を1枚描いてから保持するので実害は無い）

## 8. 相談したいこと

1. **案A・B・C のどれが妥当か。** 特に案A（提示を直す）が、
   先行実験との手続きの一貫性を崩してでもやる価値があるか
2. **案C で「進み具合の下限が 11.1%」になることをどう考えるか。**
   gamma でその見え方を薄くすれば床は作れるが、
   「進み具合11.1%の絵」と「進み具合0%の絵（真っ白）」のあいだが
   永久に測れないことになる。曲線の当てはめ上、問題になるか
3. **提示時間のばらつき**（同じ水準でも17ms〜33ms、フレーム落ちで60msのことも）を
   どう扱うべきか。`actual_ms` は記録してある
4. **方式によって s=0 の意味が違う**（ぼかしだけ字が見える）ことへの対処。
   最大ぼかしを上げる以外に筋の良い方法があるか
