> ### ⚠️ `pre_launch` を false にしないと、集めたデータが全部「テスト」になる
>
> `experiment/transfer_config.js` の `pre_launch` は「この実験はまだ掲載していない」ことを
> ページに教えるスイッチである。**true のあいだは、本番モード（URL に `?prod=1` が
> 付いた状態）で動かしても、名簿・回答・見え心地・完走レコードのすべてに
> `is_test = true` が付く。** 解析の道具（`export_transfer_firestore.py` /
> `analyze_transfer.py`）は既定で `is_test` の行を外すので、**外し忘れたまま掲載すると、
> 集計しようとした日に「0件」と出て初めて気づく**ことになる。

このスイッチを入れた理由（2026-08-21 の事故）。動作確認のつもりで開いたページから
URL のクエリ（`?group=…`）がリダイレクトで落ち、本番モード扱いで名簿に本物の行が
1件混ざった（`transfer_roster/calib_anon-eiq54sm9`。C-0b2）。当時、回答には `is_test` 列が
あったが名簿には無く、さらに**本番の連番を1つ消費して**しまっていた（連番は聴覚と視覚の
交互の振り分けを決めるので、1つずれると2集団の人数の釣り合いが崩れる）。

### 覚えておくこと: 利用許可はデプロイのたびに要ることがある

clasp で作ったスクリプトは、持ち主が一度も許可を与えていないと、そのままでは
スプレッドシートを読み書きできない。`/exec` を開くと `Authorization needed` が出て
HTTP 403 になる。直し方は、ブラウザで `/exec` を開き
**「REVIEW PERMISSIONS」→ アカウント選択 →（未確認アプリの警告が出たら「詳細」→「移動」）
→「許可」**。**これは自動化できない**（本人が画面で押すしかない）。
本番用に新しいデプロイを作ったときは、もう一度必要になる。

### どこに何を書くかの整理（`prod_common.js` を触らない理由）

| 集団の振り分けの問い合わせ | `transfer_config.js` の `roster.status_url` | `transfer.js` の `resolveAssignment()` |
| 実験1（乙課題・frac課題） | `prod_common.js` の `SUBMIT_URL`（**空のまま**） | `prod_common.js` の `post()` |

`prod_common.js` は実験1と共用なので、そこを埋めると既存の実験の保存先まで動いてしまう。

ラジオボタンと `PROD.loadState()` の戻り値から同じ規則で作り直して封筒に載せている。

### 保存基盤: **Firestore に移した**（2026-08-21）

> **いまの既定は Firestore。GAS は受け皿として残してある。**
> 名簿（採番・振り分け・重複拒否）も回答の保存も Firestore で動く。
> 上の B-1〜B-9 は**GAS へ切り戻すときにだけ必要**な手順として読む。

GAS は応答の本体を `script.googleusercontent.com` へリダイレクトして返す作りで、
この経路が**一過性で失敗して HTML を返す**ことがある（2026-08-21 に実機で発生。
サーバ自体は正常だった）。Firestore は REST を直接叩くのでこの中継が無く、
書き込みの成否もその場で分かる。速さも段違いである（名簿の問い合わせが
GAS の約6秒に対して **0.1〜0.3秒**、記録1件の書き込みが**中央値31ms**）。

| 項目 | 値 |
|---|---|
| Firebase プロジェクト | `ifont-transfer`（東京 `asia-northeast1`） |
| コンソール | https://console.firebase.google.com/project/ifont-transfer |
| ルール | `firebase/firestore.transfer.rules`（リポジトリにある） |
| ページ側の窓口 | `experiment/transfer_firestore.js` |

## J. 完走レコードと承認の判定（2026-08-21 に足した）

参加者が最後の画面（完了コードが出る画面）に着いたとき、**1セッション1行の
「完走レコード」**を送るようにした。承認の判定はこの1行だけで済む。

| 入る場所 | `transfer_wellbeing`（既存のコレクション。新しい入れ物は作っていない） |
|---|---|
| 見分け方 | `record_kind` 列が `session` |
| 入っているもの | `completion_code` / `phase` / `group` / `n_trials`（答えた問題数）／ `duration_s`（所要秒）／ `send_failures`（送れなかった記録の件数）／ `send_retries` / `version` |

`transfer_wellbeing` には3種類の行が混ざるので、**`record_kind` で選り分けること**。

| `record_kind` | 中身 | 分析に使うか |
|---|---|---|
| `final`（または空） | 見え心地の回答。1参加者1行 | **使う** |
| `clip` | 群Cの1本ぶんの中間レコード（12行／人） | 使わない（保険） |
| `session` | 完走レコード | 使わない（承認の判定に使う） |

- [ ] **J-1 承認作業は `record_kind = "session"` の行で行う**。1問1行の記録の行数から
      「完走したか」を推測しない（通信が悪くて取りこぼした人を非承認にしてしまう）。
- [ ] **J-2 `send_failures` が 0 でない人を数える**。掲載後に必ず見ること。
      多いようなら通信の作りに問題がある。**その人にも報酬は払う**（本人の落ち度ではない）。
- [ ] **J-3 群Cは1参加者1レコードなので、送信が落ちると全損になる**——だったのを
      2026-08-21 に直した。いまは (1) 送信を待って作り直す (2) それでも駄目なら
      完了コードを出す前に「送れませんでした・再送する」の画面を出す

      問い合わせてください」と案内する、の3段構えになっている。

      参加者から「コードは出たが送れなかったと言われた」という問い合わせが来たら、
