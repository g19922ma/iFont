## 2. 切り出し数と読み順の推定

### 切り出し数

**217区間**。周回の切れ目（1.6秒以上の無音）で3つに割れ、**74 + 72 + 71** だった。

### 読み順

**五十音表をそのまま、頭から3周**。1周＝71字で、内訳は

```
あいうえお かきくけこ さしすせそ たちつてと なにぬねの はひふへほ まみむめも
やゆよ らりるれろ わ を ん
がぎぐげご ざじずぜぞ だぢづでど ばびぶべぼ ぱぴぷぺぽ
```

= 清音46（を・んを含む）＋濁音20＋半濁音5 = **71**。

手順書の「優先12字（あ い か が ぱ ば た だ し す ま な）を先に読む」順**ではなかった**。
また手順書は「を・ぢ・づ・ゔ を除く68字」を指定していたが、話者は五十音表を素直に読んだため
**を・ぢ・づ が入っている**（ゔ は無い）。実験で使うのは68字なので、余分な3字は捨てればよい。

### 何を根拠にそう言えるか（自動照合の中身）

読み順は耳で聞かずに次の方法で当てた。母音（あ/い/う/え/お）は
**フォルマント**（声道の共鳴周波数。母音ごとに固有のパターンを持つ）で機械的に見分けられる。
そこで

1. 各区間のいちばん大きい60msから F1・F2（低いほうから2つの共鳴周波数）を測る
2. 五十音表71字の並びを「期待される母音の並び」（あいうえお あいうえお …）に直す
3. 両者を DP（動的計画法。挿入だけ許す対応づけ）で照合し、**余分な区間がどこか**を決める

結果、**周3（71区間）は挿入ゼロで71字にぴったり一致**した。この周を基準に話者の母音の重心を測り直して
周1・周2を照合すると、周1に3個・周2に1個の余分な区間が見つかり、
**74−3 = 71、72−1 = 71** と辻褄が合う。3周とも同じ並びで読まれたと考えて矛盾がない。

> 注: これは自動推定であって確定ではない。特に鼻音（な行・ま行・ん）と濁音は
> フォルマントが崩れて確信度が下がる（§6の要確認リスト）。**確定は人の耳で行う**。

## 5. 問題点

### 5-1. 50Hzの電源ハム（**音質面で唯一の実質的な問題**）

発話と発話のあいだの無音（合計138.6秒）を集めて測った結果:

| | 無音のRMS |
|---|---|
| 素のまま | **−26.3 dBFS** |
| 60Hzハイパス後 | −36.2 dBFS |
| 80Hzハイパス後 | −39.1 dBFS |
| **100Hzハイパス後** | **−42.8 dBFS** |
| 120Hzハイパス後 | −46.7 dBFS |

無音のエネルギーの内訳は **45–55Hz に 86.3%**、60Hz以下に合わせて **92.3%**。
つまり「雑音」の正体はほぼ全部が電源ハム（コンセントの周波数。東日本の50Hz）であり、
声の帯域（300–3000Hz）に入っている雑音は **0.2%** しかない。

発話のRMS中央値は −16.0 dBFS なので、

- 素のまま: **SN比 約10 dB**（唸りが声のすぐ下まで来ている）
- 100Hzハイパス後: **SN比 約27 dB**
- 120Hzハイパス後: **SN比 約31 dB**

話者の声の高さ（F0）は **中央値216 Hz（5〜95%点で185〜237 Hz）** なので、
**100Hzでも120Hzでも声そのものには一切かからない**。

**この実験では見過ごせない**。ゲーティング法（音を途中で打ち切って「どこまで聞けば分かるか」を測る方法）では
刺激の頭の数十msだけを聞かせる条件があり、そこは音が小さい。SN比10dBのままだと
「短い条件では唸りしか聞こえない」ことになりかねない。

> **対応方針（要承認）**: 刺激を書き出す段階で **100Hzのハイパスフィルタ**を全字共通で掛ける。
> 掛ける・掛けないは全字・全時点で統一し、論文に明記する。
> 今回の切り出しWAVは**無加工のまま**残してあるので、後段で掛ければよく、録り直しは不要。

### 5-4. acoustic onset 検出の実装メモ（計画書からのずれ）

計画書3.4-4の文言は「**1ms窓**の短時間エネルギーが背景雑音床+10dBを一定時間連続で超えた最初の時点」。
実装では **時間分解能は1msのまま（刻み1ms）、窓長だけ5ms** にしている。

理由: 1ms窓のRMSは発話の途中でもしきい値をまたいで激しく上下するため、
「10ms連続で超える」がほとんど成立せず、**弱い子音の頭を飛ばして母音まで進んでしまう**。
実測で、文字どおりの1ms窓では20区間がこの症状を起こしたが、5ms窓では14区間に減った。
計画書どおりの1ms窓で出したい場合は `--onset-win-ms 1` を付ければよい（両方出して比べられる）。

背景雑音床は**全体ではなく区間ごと**に、その区間の直前300ms（＝発話と発話のあいだの無音）から測っている。
しきい値は計画書どおり **その床 + 10 dB**。

なお onset 検出は §5-1 のハイパス後の波形で行っている（素のままだと50Hzハムが
床を−26dBまで押し上げてしまい、+10dB では何も検出できない）。**切り出す音自体は無加工**。

## 9. 採用テイクと本番の下処理

### 9-1. テイク選択（事前基準・計画書3.4-2）

音割れの回を除き、残りから**発話長が中央値に最も近い回**を機械的に採用。

### 9-2. ハイパスフィルタ（適用の記録）

| 項目 | 値 |
|---|---|
| 遮断周波数 | **100 Hz**（丸山承認済み・全字共通） |
| 種類・次数 | バターワース 4次 |
| 掛け方 | **ゼロ位相**（`sosfiltfilt`。前後に往復させて位相のずれを打ち消す） |
| 掛ける対象 | 採用テイク68字すべて。字ごとの調整はしない |

ゼロ位相にした理由: ふつうのフィルタは周波数ごとに遅れ方が違うので、**音の立ち上がりが
時間的にずれる**。この実験は onset を0msの基準にするため、頭が数msずれるだけで測定が狂う。

効果: 発話と発話のあいだの雑音が **−26.3 → −42.8 dBFS**（§5-1）。
話者の声の高さは216 Hzなので100 Hzで切っても声には掛からない。

### 9-3. 音量合わせ（適用の記録）

計画書3.4-3 のとおり「1音まるごとに**一定の倍率**を掛けるだけ」。音の中身の強弱の配分は変えない。

| 項目 | 値 |
|---|---|
| 合わせ方 | 全字の RMS（onset〜区間末）をそろえる |
| そろえた先 | **−22.12 dBFS** |
| 倍率の範囲 | **0.273 〜 1.000 倍**（すべて1.0以下＝**増幅は一切していない**） |
| 処理後のピーク | 最大 **−8.49 dBFS**（上限 −3 dBFS に対して余裕あり） |
| 処理後のRMS | 全68字 −22.12 dBFS（ぴったり一致） |

**なぜ −22.12 dBFS なのか**: 「増幅しない（倍率1.0以下）」を守ったまま全字を同じRMSにそろえると、
合わせ先は自動的に**いちばん小さい字**の水準になる。この録音では「**す**」（倍率1.000＝無加工）。
つまり全字を「す」に合わせて下げた。

> ピーク上限（−3 dBFS）は**一度も効いていない**。効いたのは「増幅しない」という条件のほうで、
> 結果のピークは最大でも −8.5 dBFS と十分低い。音割れの心配はない。

赤い縦線が採用した onset、灰色の破線が**検出用フィルタを変えたときの位置**（120Hz・200Hz）。

**見るところは「赤い線が子音の始まりに立っているか」。** 子音より後ろ（母音の頭）に
立っていたら遅すぎる。`▶ onsetから` を押して**頭が切れて聞こえたら、その字は遅い**。

### 10-1. onset検出の設定（計画書3.4-4）

| 項目 | 値 |
|---|---|
| 判定 | 短時間エネルギーが「背景雑音床 +10 dB」を **10 ms連続**で超えた最初の時点 |
| 窓長 / 刻み | 5 ms / 1 ms（§5-4。文字どおりの1ms窓では成立しないため） |
| 背景雑音床 | 区間ごとに、その直前300 msから測る |
| **検出用ハイパス** | **150 Hz**（配信する音の100 Hzとは**別**） |

> **配信用（100 Hz）と検出用（150 Hz）を分けた理由**は、実測で分かった副作用にある。
> 100 Hz では50Hzハムの残りで背景雑音床が4〜7 dB持ち上がり、しきい値（床+10 dB）も
> その分きつくなる。すると**立ち上がりのなだらかな摩擦音の頭を30〜50 ms取りこぼす**
> （さ:+31 / し:+33 / す:+31 / そ:+52 / ふ:+38 ms も遅くなった）。
> 150 Hz ならハムはほぼ消え、話者のF0（216 Hz）には掛からない。
> これで「onsetが頭から85ms超」の字は **10字 → 4字** に減った。
> 配信する音は承認どおり100 Hzのままで、**変えたのは測り方だけ**。

|---|---|---|---|---|

## 12. ハマったところ・次回への教訓

- **「無音区間」が−26dBもあって最初は区間検出が全く成立しなかった。**
  原因は50Hzの電源ハム。周波数を見るまで「ひどい雑音の録音だ」と誤読しかけた。
  → **エネルギーだけ見て雑音の量を判断しない。まずスペクトルを見る。**
  ハムは声の帯域には入っていないので、実際の録音品質はむしろ良い。
- **読み順は「ファイル名から五十音順だろう」と決め打たず、フォルマントで機械的に照合した。**
  結果、手順書と違って を・ぢ・づ が入っていることが分かった。
  1周が68字か71字かを間違えると全ラベルが3つずれる。
  → **仕様書に書いてある想定と実物が違うことがある。実物で確かめる。**
- **話者の申告（「が」「ぎ」が逆）は正しかったが、「録音全体で」ではなく「周1だけ」だった。**
  申告をそのまま3周に適用していたら、周2・周3を**わざわざ間違った状態にしていた**。
  → **人からの申告も、そのまま全体に適用せず範囲を測って確かめる。**
  申告があったから測ったのではなく、申告の**前**に自動照合が同じ2区間を
  「確信度が低い」と印をつけていた（cost 1.19 と 2.38）。
  → **自動チェックの「怪しい」印は実際に当たる。潰す価値がある。**
- 順序の乱れは「が・ぎ」以外にもないかを、隣接ペアの総当たりで走査した。
  改善量は が・ぎ の 3.00 が突出しており、次点は 2.12。
  **1件の申告をきっかけに同種の乱れを全体で探す**のは安く、やっておく価値がある。
- **onset検出の「1ms窓で連続」は文字どおり実装すると動かない**（1msのRMSは上下が激しすぎる）。
  計画書の文言と実装のずれは §5-4 に明記した。論文にもこの形で書く必要がある。
- 確認ページの音声再生は `<audio>` + data URI ではなく **Web Audio** にした。
  `<audio>` はタブの状態によって読み込まれないことがあり、無音のまま原因が分かりにくい。
- **自動処理の「怪しい」印は、人が実際に直した箇所とほぼ一致した。**
  訂正が必要だった3区間のうち2区間は「onset検出不能・異常に短い」「余分」と印がついていた箇所。
  「が」「ぎ」の入れ替わりも、申告の前に「確信度が低い」と印がついていた。
  → **印を出すことより、印を潰す作業を人の手順に組み込むことに価値がある。**
- **配信する音のフィルタと、測るためのフィルタは分けてよい**（分けるべきだった）。
  承認された100Hzハイパスをそのまま onset 検出にも使ったところ、ハムの残りで背景雑音床が
  4〜7dB持ち上がり、摩擦音の頭を30〜50ms取りこぼした。検出だけ150Hzにしたら解決した。
  → **「同じ処理を使い回すほうが一貫している」とは限らない。目的が違えば設定も違う。**
- **onsetは1点に決まらない字がある。** 検出用フィルタを120/150/200Hzと振ると、
  摩擦音や有声破擦音では最大37msも動いた。逆に破裂音・母音はほぼ動かない。
  → **1つの数字を出して終わりにせず、「どれくらいぶれるか」も一緒に出す。**
  ぶれの大きさがそのまま「人が目で見るべき優先順位」になる。
- 音量合わせで効いた制約は、ピーク上限（−3dBFS）ではなく「**増幅しない**」のほうだった。
  結果として全字が「いちばん小さい字（す）」に合わせて下がった。
  → 制約を2つ置いたら、**どちらが実際に効いたのかを確かめて記録する**。
