# 1. 較正フェーズ（群Acal・群A′）の掲載文

- 対象ページ: `experiment/transfer_calib.html`（`phase=calib`、群Acal＝聴覚・群A′＝視覚に自動振り分け）
- 正本の計画: 4.1（全体の流れ）・4.3（課題の詳細）・付録Q4（基準アニメの長さ）

## 1.1 このフェーズは何をするか

音声または画面上の文字を**とても短い時間だけ**提示し、参加者に五十音表から選んでもらう。
その正答率が、提示時間（聴覚）・進み具合（視覚）に応じてどう上がっていくかを字ごとに測る。
この「正答率の曲線」が、あとの生成工程（曲線をもとに文字アニメーションの進み方を作る）の
材料になる（計画書 4.1 の生成工程）。

## 1.2 運用: 16人ぶん集まった時点で一度確認する

1. 掲載サイトの管理画面で、**募集人数の上限をいったん16人に設定して**掲載する
   （サイト側に上限を厳密に途中で止める機能が無い場合は、16件目の完了コードが
   提出された時点で募集を手動で一時停止する）。
2. 16人ぶんの記録（`transfer_trials`）を取り出し、次を確認する。
   - 打ち切りなしの問題（確認問題A・全部聞かせる／全部見せる）の正答率が十分高いか
     （低いと録音や画面側に問題がある——計画書 4.4-7）。
   - 字ごとの曲線が、いちばん早い時点で正答率が十分低く（床が取れているか）、
     全長で正答率が十分高いか（天井が取れているか）。
   - 1人あたりの実際の所要時間が、下の見込み（聴覚約11.5分・視覚約8.5分）から
     大きくずれていないか。
3. **問題なければ**、募集人数の上限を外し（または人数シミュレーション「A2」で確定した
   全体人数まで）残りを追加募集する。
4. **問題があれば**、掲載を一時停止し、`experiment/transfer_config.js` を直して
   `config_version` を上げてから再掲載する。この場合、直す前に集まった分は
   較正データの本体には使わず、設計を決めるための参考情報として扱う。

> 参加者から見ると、掲載は1本の募集としてずっと同じに見える（募集人数の上限が
> 途中で変わって見えるだけ）。「これは下見です」という案内は出さない。

## 1.5 承認・非承認の目安（掲載側の作業）

| 判断 | 条件 |
|---|---|
| 承認 | 提出された完了コードが、**完走レコード**（`transfer_wellbeing` の `record_kind = "session"` の行の `completion_code` 列。`phase = "calib"`）にある |
| 承認（データは分析から外す） | 完走レコードはあるが、打ち切りなしの問題（確認問題A）を落としている等、回答の質が低い |
| 非承認 | 完了コードが記録に無い／他の人のコードと重複している |

- **完走レコードは、最後の画面（完了コードが出る画面）に到達したときに1行だけ入る。**
  だから「最後まで到達したか」を1問1行の記録の行数から推測しなくてよい。
  同じ行に、答えた問題数（`n_trials`）・所要秒（`duration_s`）・
  **送信できなかった記録の件数**（`send_failures`）も入っている。
- `send_failures` が 0 でない人は、通信が悪くて1問1行の記録を取りこぼしている。
  **報酬は払う**（本人の落ち度ではない）。分析に足りるかは別に判断する。
- 完了コードが完走レコードに無いのに参加者がコードを持っている場合は、
  送信がすべて失敗した可能性がある。その場合、参加者の画面には
  「このコードと時刻を控えて問い合わせてください」という案内が出ているので、
  問い合わせの有無と時刻を突き合わせて判断する。
- **「データを分析から外す」ことと「報酬を払わない」ことは別**にする。最後までやってくれた人には払う。

## 1.6 較正フェーズが終わったらすること

**（a）16人ぶん集まった時点**（→ 1.2 の確認。続行の可否だけを見る簡易チェック）

1. 打ち切りなしの問題の正答率を字ごとに出す。低い字があれば録り直す（別の字に差し替えない）。
2. 1人あたりの実所要時間の中央値を出し、11.5分・8.5分の見込みと大きくずれていないか確認する。
3. 字ごとの曲線が天井・床を捉えられているか（→ 1.2）を見て、続行か一時停止かを判断する。

**（b）較正フェーズ全体が終わった時点**（人数シミュレーション「A2」で確定した全体人数に達したあと）

1. 視覚の回答から、基準アニメの長さ（今は暫定600ミリ秒）を決める。
2. **速さの効きめ（RQ4）の当たりを見る**。`transfer_trials` の `base_anim_ms` 列で
   群A′フェードの回答を2つに分け、同じ進み具合の水準での正答率を比べる。差は効果量と
   信頼区間で書く。あわせて、**本番の群A′の人数だと信頼区間がどのくらいの幅に
   なるか**を見積もる（計画書 3章 RQ4・10章⑦）。
3. **内挿の確認**。較正の提示水準を1つずつ伏せて曲線を当てはめ直し、伏せた水準の正答率を
   予測できるかを見る（追加データは要らない）。大きく外れる水準があれば、水準を
   足すか配置を変える。
4. 上記をシミュレーション「A2」に入れて、打ち切り時刻・まぎれ字の量・検証フェーズの必要人数を確定する。
5. 確定した数値を `experiment/transfer_config.js` に入れ、`config_version` を上げる。
   **生成に使う視覚の曲線は600ミリ秒の水準だけ**と事前に決めてあるので、
   速さ2水準を測っていても生成の中身は左右されない（計画書 7.1）。
6. 生成のコード・設定・全8字の進み方を**凍結**（検証データを取る前にコミットで固定し、
   番号を記録する）。**視覚（群B）の打ち切り時点 `visual.gates_ms` を、聴覚と同じ
   字ごとの配置へそろえる**（検証フェーズの掲載前に必要。→ 2章）。
7. 検証フェーズ・群Cの掲載準備に進む（→ 2章・3章）。

## 2.1 ⚠ 掲載前の必須条件（まだ満たしていない）

検証フェーズは、**較正フェーズの生成・凍結が終わったあとでないと掲載できない**（1.6の手順が前提）。
特に次の1点は、2026-08-22時点でまだ着手していない技術的な前提条件である。

> **視覚（群B）の打ち切り時点 `visual.gates_ms` が、まだ全字共通の暫定値のままである。**
> 聴覚（群Atest）は8/21に「字の音の種類ごとの時点帯」へ切り替え済みだが、視覚側は
> 旧来のままになっている（`experiment/transfer_config.js` の `visual.gates_ms._default` を参照）。
> 群Bと群Atestの曲線を同じ時点で比べる決まりになっている（計画書 4.3）ため、
> **この整合を取らないまま検証フェーズを掲載すると、聴覚と視覚の曲線を正しく比較できない。**
> 較正フェーズの分析（→ 1.6 の②③④）で字ごとの配置を確定したあと、その配置を
> `visual.gates_ms` にも書き写してから掲載すること（`project/実験計画書_転写検証.md` 11章）。

問題数（下表の94問）は上記の整合を取っても変わらない見込みである（1字あたりの時点の**数**は
変えないため）。ただし**掲載直前に必ず `check_transfer_stimiuli.js` を再実行して確認**すること。

## 2.2 このフェーズは何をするか

## 3.1 群Cとは何か（なぜ別の掲載にするのか）

5字続けるときは**前の字が現れきってから0.3秒空けて**次が出る
