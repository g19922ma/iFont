## 1. なぜ移すのか

**GAS には一過性の失敗がある。** 2026-08-21 に実機で「サーバに接続できませんでした」の
お断り画面が出た。直後に `curl` で叩くとサーバは正常だった。GAS は応答の本体を
`script.googleusercontent.com` へリダイレクトして返す作りで、この経路がときどき失敗し、
JSON のかわりに HTML のエラーページを返す。1回で諦める作りだったため、
**サーバが動いているのに参加者を取りこぼしていた**。

Firestore は REST を直接叩くので、この中継が無い。書き込みの成否もその場で分かる。

ただし移すには、いま GAS がやっている**採番と重複チェックを作り直す**必要がある。
そこが今日の日程に載るかどうかが判断の分かれ目になる（→ 4章）。

## 2. 当座の手当て（実装済み・2026-08-21）

移行を待たずに、一過性の失敗そのものは潰した。

- **名簿の問い合わせを3回まで作り直す**（0.8秒 → 2秒 → 4秒、散らし付き）。
  3回とも失敗して初めてお断り画面へ。
- **JSON でない応答も失敗として数える。** HTML が返ってきたら作り直す。
  これが実機で起きた現象の本体だった。
- **お断り画面に「もう一度試す」ボタン**を付けた。押すと問い合わせからやり直し、
  通ればそのまま実験に進める。
- **何回目で通ったかを記録に残す。** `assign_source` 列が `server`（1回目）/
  `server:retry2` / `server:retry3` になるので、掲載後に頻度を数えられる。
- **回答の送信も3回まで作り直す**（0.8秒 → 2.5秒 → 6秒）。

設定は `transfer_config.js` の `roster.retry` と `logging.retry`。

## 3. Firestore での作り方（設計）

参加者のブラウザは**ログインしない**。ログインを入れると同意の前に個人の識別が
発生してしまい、いまの倫理設計と噛み合わないためである。
そこで「認証なしでも安全に書ける形」をルールで作る。ルールは
`firebase/firestore.transfer.rules` に置いた。

### 3.1 重複参加のチェック — 「作れるかどうか」で判定する

名簿は `transfer_roster/<フェーズ>_<参加者ID>` の1人1ドキュメント。
ルールは **create だけ許可、read は禁止**。

Firestore は既にあるドキュメントへの create を必ず失敗させる。つまり
**「作れたら初参加、作れなければ再訪」**が、読み出しを許さずに分かる。
検証フェーズでは `calib_<参加者ID>` の作成も試み、そちらが失敗したら
「較正フェーズに参加済み」＝お断り、と判定できる。

> GAS 版は名簿シートを頭から読んで突き合わせていた。人数が増えるほど遅くなるうえ、
> 全参加者の記録を1回の応答で読める作りでもあった。この方式はどちらも解消する。

#### ⚠ 3.1 の追記（2026-08-21・実装して分かったこと）

**上の「読み出しを全面禁止のまま判定する」案は成り立たなかった。** 実装したのは
**名簿だけ1件ずつの読み出し（`get`）を許す**形である。理由は2つ。

1. **開き直した人に、前と同じ集団・同じ連番を返せない。**
   create が失敗したことは分かるが、「では何に割り当てられていたか」が分からない。
   別の集団で再開させると、音声と視覚の人数の釣り合いが崩れ、字×条件の割付
   （連番から決まる）も食い違う。GAS 版はこれを `returning: true` で返していたので、
   読めない設計にすると**機能が後退する**。
2. **フェーズをまたいだ重複参加を、確かめるためだけの create で判定できない。**
   「較正に出た人が検証へ来たら断る」を create の成否で見ると、
   **断るべき人を較正の名簿に載せてしまう**（あとで数を数えるときに濁る）。

かわりに次のようにした。

```
match /transfer_roster/{doc} {
  allow get: if true;          // ドキュメントIDを名指しでの1件読みだけ
  allow create: if isRoster(request.resource.data);
  allow list, update, delete: if false;   // 一覧・書き換え・削除は禁止
}
```

これで守れているもの。

- ドキュメントIDは `<フェーズ>_<参加者ID>` なので、**参加者IDを知っている人しか引けない**
- `list`（一覧・検索）は禁止のままなので、**名簿を端から舐めることはできない**
- 名簿の中身は割り当てだけ（フェーズ・集団・連番・作業者ID）で、**回答は入らない**
- 回答（`transfer_trials` / `transfer_wellbeing`）は**読み出し全面禁止のまま**

つまり緩めたのは「割り当ての情報を、参加者IDを知っている人が1件だけ引ける」ところまでで、
回答データの秘匿性は当初の設計から下がっていない。

#### 実装した手順（4段）

順番に意味がある。`experiment/transfer_firestore.js` の `resolveAssignment()`。

1. 同じフェーズの名簿に自分がいたら、**そのときの割り当てをそのまま返す**（開き直し）
2. 断るべきフェーズの名簿に自分がいたら、断る
3. 採番する（**ここで初めて番号を消費する**ので、断られた人は番号を使わない）
4. 名簿に載せる（`exists: false` の条件付き。同時に2つのタブから来たら先着を正とする）

### 3.2 採番 — 「1だけ増やす」書き込みの応答から番号を受け取る

集団の釣り合い（較正なら Acal と A′ を交互）には通し番号が要る。
`transfer_counters/<フェーズ>` の `n` を、Firestore の **increment 変換**で 1 増やす。

```
POST https://firestore.googleapis.com/v1/projects/<PROJ>/databases/(default)/documents:commit?key=<KEY>
{ "writes": [{
    "transform": {
      "document": ".../transfer_counters/calib",
      "fieldTransforms": [{ "fieldPath": "n", "increment": { "integerValue": "1" } }]
    }}]}
```

**応答の `transformResults` に、増やしたあとの値が入って返る。**
だから読み出しを許さなくても自分の番号が分かる。あとは現行と同じ規則で
`group = groups[n % 2]`、`assign_index = floor(n / 2)` を出す。

increment はサーバ側で不可分に処理されるので、同時に来ても番号は衝突しない。
**トランザクションを組む必要がない**のがこの方式の利点である。
ルール側で「`n` が 1 だけ増える更新」に限っているので、番号を飛ばしたり
巻き戻したりもできない。

### 3.3 回答の保存

`transfer_trials` に1問1ドキュメント、`transfer_wellbeing` に1参加者1ドキュメント。
どちらも **create だけ許可、read/update/delete は禁止**。
最低限の列が入っているかもルールで見る（形の決まらない書き込みで荒らされないため）。

### 3.4 GAS はどうするか

**当面は二重書き込みで残す**（保険）。ただし**必須依存にはしない**——
GAS への送信が失敗しても実験は続き、Firestore に入っていれば解析できる形にする。
実データで Firestore 側に全件入ることを確認できたら、GAS を落とす。

### 3.5 解析側

`analyze_transfer.py` は「dump JSON / CSV」を読む作りにしてあるので、
**取り出し方が変わっても分析側は変えなくてよい**。

実装したのは `experiment/tools/export_transfer_firestore.py`。
GAS のスプレッドシートを CSV に保存したときと**同じ列名・同じ並び**で出すので、
`analyze_transfer.py` にそのまま渡せる。

## 5. 日程の判断（2026-08-21 時点の推奨）

> **下見は GAS ＋ 再試行のまま出すことを勧める。Firestore 移行は下見のあと。**

理由。

- **今日の failure は再試行で塞がった。** 実機で起きたのは一過性の失敗で、
  3回作り直す実装と「もう一度試す」ボタンで、参加者を取りこぼす経路は無くなった。
  ローカルで障害を再現して確認済み（HTMLが返る状況→3回試して失敗→ボタンで復帰）。
- **Firestore はまだプロジェクトすら無い。** 4章のとおり、人の手作業が先に要る。
  キーが揃うまでコード側は書いても試せない。
- **下見の目的は運用の確認**である。16人で「掲載→回答→完了コード→回収」が回るかを
  見るのが主眼で、保存基盤が GAS か Firestore かは目的に関わらない。
- **未検証の採番機構を、有償の参加者募集の直前に入れるのは割に合わない。**
  採番と重複チェックは間違えると取り返しがつかない（番号の重複・誤ったお断り）。
  下見で GAS を回している裏で作り、本番（較正・検証フェーズ）から使うのが安全である。

**撤退線の扱い**: 8/22 昼の時点で Firestore が完成していなくても、
現行構成は**そのまま下見に出せる状態を保ってある**。今回の変更は再試行の追加だけで、
GAS 側にも設定にも壊れる変更を入れていない。

> **5章への追記（同日夜）**: 上の判断は「Firestore がまだ無い」ことを前提にしていたが、
> その後 4.1 のとおり短時間でプロジェクトが作れ、6章の確認まで通った。
> **どちらでも出せる状態になった**ので、日程の判断は「切り替えを間に合わせる」から

## 6. 疎通と負荷の確認（2026-08-21 に実施・すべて合格）

`node experiment/tools/test_transfer_firestore.js` で **32項目すべて合格**。
確かめたことと結果は次のとおり。

| 見たこと | 結果 |
|---|---|
| 連続16人の採番 | acal 8人 / aprime 8人。**交互に配られ**、連番は 0..7 で飛びも重複もなし |
| 開き直し | 同じ参加者IDは**同じ集団・同じ連番**に戻る。かつ**番号を消費しない** |
| 24人が同時 | 24件すべて成功。「集団＋連番」が24通りすべて別。飛びなし。12人 / 12人 |
| 60人が同時（別途） | 60件すべて成功（1.2秒）。一意な割り当て 60/60。30人 / 30人 |
| 重複拒否・較正→検証 | 断る（`already_in_calib`） |
| 重複拒否・較正→群C | 断る（`already_in_other_phase`） |
| 重複拒否・群C→検証 | 断る（`already_in_comfort`） |
| 重複拒否・検証→群C | 断る（`already_in_other_phase`） |

| 回答30件 | 全件入る |
| 見え心地 | 入る（`transfer_wellbeing`） |
| ルール: 回答の一覧 | 読めない（403） |
| ルール: 名簿の一覧 | 読めない（403）。1件読みだけ 200 |
| ルール: カウンタの読み | 読めない（403） |
| ルール: 名簿の書き換え | できない（403） |
| ルール: 採番を100飛ばす | できない（403） |
| ルール: 列の足りない回答 | 入らない（403） |
| ルール: 決めた4か所以外 | 書けない（403） |

**速さ**（東京に置いたので GAS より2桁速い）。

| | GAS | Firestore |
|---|---|---|
| 名簿の問い合わせ | 約6秒 | **0.1〜0.3秒** |
| 記録1件の書き込み | 応答を読めない | **中央値 31ms**（最小25 / 最大91） |

**実物のページでも確認した**（`transfer_calib.html` と `transfer_comfort.html` を
ブラウザで開いて）。

- 較正の入口: 集団 `acal`・連番あり・`assign_source` は `firestore`
- 群Cの入口: 集団 `c`・`assign_source` は `firestore`
- どちらも回答・見え心地の送信が通る。**コンソールにエラーなし**
- キャッシュを消して開き直すと、サーバから同じ割り当てが返る
- **Firestore をわざと壊すと GAS に落ちて続行できた**（`assign_source` が `gas-fallback`。
  Firestore を3回試して約7秒 → GAS が応答、合計9.7秒）

> **負荷について注意が1つ。** 1つの Node プロセスから同時に300本の接続を張ると
> 半分ほど失敗する。これは **Firestore ではなく Node の fetch が一度に張れる
> 接続数の頭打ち**である（同時100本までなら300件全部通る）。ブラウザは
> 1つのサーバに6本程度しか同時に張らないうえ、参加者ごとに別の機械なので、
> 実際の掲載でこの形にはならない。加えてページ側には3回の作り直しが入っている。

試し打ちの行は `is_test = true` が付き、`python3 experiment/tools/purge_transfer_firestore.py --yes`
で消せる（本物の行には手が届かない）。確認後に消し済み。

## 7. 切り替えと切り戻しのしかた

### いまの既定

`transfer_config.js` の `backend`:

```js
backend: {
  roster:  "firestore",   // 名簿を Firestore に聞く
  logging: "firestore",   // 記録を Firestore に入れる
  fallback: true,         // 主が全部だめなら、もう一方も試す
  dual_write_logging: false,
}
```

### GAS に戻したいとき（切り戻し）

**2行変えるだけでよい。**

```js
roster:  "gas",
logging: "gas",
```

GAS のコードもデプロイも `/exec` URL も**そのまま残してある**ので、これで
2026-08-20 の構成に戻る。**ただし群C（`comfort` フェーズ）だけは、GAS を
デプロイし直さないと動かない**（`gas_transfer/code.gs` に規則は書いたが、
`clasp push -f` → `clasp deploy` がまだ）。較正・検証フェーズは今すぐ戻せる。

> ページの `?v=` を上げるのを忘れないこと。`transfer_config.js` を変えたら
> `transfer_calib.html` / `transfer_test.html` / `transfer_comfort.html` の
> `?v=` を全部上げる（掲載前チェックリスト B-9b）。

### 移行の見極め期間だけ両方に入れたいとき

`dual_write_logging: true` にすると、主に入ったあと**もう一方にも同じものを送る**。
両方に同じ件数が入るかを確かめるためのもので、常用はしない
（GAS の同時実行30本の上限に当たるため）。

### どちらで通ったかは記録に残る

`assign_source` 列を数えれば、掲載後に頻度が分かる。

| 値 | 意味 |
|---|---|
| `firestore` | Firestore が主で、1回目で通った |
| `firestore:retry2` `firestore:retry3` | Firestore が主で、2回目・3回目で通った |
| `gas-fallback` | Firestore がだめで GAS に落ちて通った（**ここが増えたら要調査**） |
| `server` `server:retry2` | GAS が主で通った（2026-08-20 までと同じ表記） |
| `cache` | 同じ端末で前に決まった割り当てを使った |
| `local_hash` | サーバに繋がらず、参加者IDから手元で決めた（`require_server` が false のときだけ） |

## 8. この移行が終わった状態

- 参加者のブラウザ → Firestore（直）。中継が無いので一過性の失敗が起きにくい。
- 採番は increment 変換で衝突しない（**トランザクションを書く必要がなかった**）。
- 重複チェックは名簿の1件読みで判定。3方向すべて塞がっている。
- 回答の読み出しは全面禁止。名簿だけ1件読みを許す（3.1 の追記を参照）。
- GAS は受け皿として残してある。設定2行で主に戻せる。
- 実験1（68かな・220人規模）はこの上で回せる（コレクション名を分ければ同居できる）。
