# 転写検証実験の保存基盤を Firestore へ移す計画

- 作成: 2026-08-21 丸山。決定は「**最終的には Firestore 一本化**」。
- 現状: 保存も名簿も GAS ウェブアプリ（`gas_transfer/`）。
- この文書は「なぜ移すか」「どう作るか」「いま人が何をする必要があるか」をまとめたもの。

---

## 1. なぜ移すのか

**GAS には一過性の失敗がある。** 2026-08-21 に実機で「サーバに接続できませんでした」の
お断り画面が出た。直後に `curl` で叩くとサーバは正常だった。GAS は応答の本体を
`script.googleusercontent.com` へリダイレクトして返す作りで、この経路がときどき失敗し、
JSON のかわりに HTML のエラーページを返す。1回で諦める作りだったため、
**サーバが動いているのに参加者を取りこぼしていた**。

Firestore は REST を直接叩くので、この中継が無い。書き込みの成否もその場で分かる。

ただし移すには、いま GAS がやっている**採番と重複チェックを作り直す**必要がある。
そこが今日の日程に載るかどうかが判断の分かれ目になる（→ 4章）。

## 2. 当座の手当て（実装済み・2026-08-21）

移行を待たずに、一過性の失敗そのものは潰した。

- **名簿の問い合わせを3回まで作り直す**（0.8秒 → 2秒 → 4秒、散らし付き）。
  3回とも失敗して初めてお断り画面へ。
- **JSON でない応答も失敗として数える。** HTML が返ってきたら作り直す。
  これが実機で起きた現象の本体だった。
- **お断り画面に「もう一度試す」ボタン**を付けた。押すと問い合わせからやり直し、
  通ればそのまま実験に進める。
- **何回目で通ったかを記録に残す。** `assign_source` 列が `server`（1回目）/
  `server:retry2` / `server:retry3` になるので、掲載後に頻度を数えられる。
- **回答の送信も3回まで作り直す**（0.8秒 → 2.5秒 → 6秒）。

設定は `transfer_config.js` の `roster.retry` と `logging.retry`。

## 3. Firestore での作り方（設計）

参加者のブラウザは**ログインしない**。ログインを入れると同意の前に個人の識別が
発生してしまい、いまの倫理設計と噛み合わないためである。
そこで「認証なしでも安全に書ける形」をルールで作る。ルールは
`firebase/firestore.transfer.rules` に置いた。

### 3.1 重複参加のチェック — 「作れるかどうか」で判定する

名簿は `transfer_roster/<フェーズ>_<参加者ID>` の1人1ドキュメント。
ルールは **create だけ許可、read は禁止**。

Firestore は既にあるドキュメントへの create を必ず失敗させる。つまり
**「作れたら初参加、作れなければ再訪」**が、読み出しを許さずに分かる。
検証フェーズでは `calib_<参加者ID>` の作成も試み、そちらが失敗したら
「較正フェーズに参加済み」＝お断り、と判定できる。

> GAS 版は名簿シートを頭から読んで突き合わせていた。人数が増えるほど遅くなるうえ、
> 全参加者の記録を1回の応答で読める作りでもあった。この方式はどちらも解消する。

### 3.2 採番 — 「1だけ増やす」書き込みの応答から番号を受け取る

集団の釣り合い（較正なら Acal と A′ を交互）には通し番号が要る。
`transfer_counters/<フェーズ>` の `n` を、Firestore の **increment 変換**で 1 増やす。

```
POST https://firestore.googleapis.com/v1/projects/<PROJ>/databases/(default)/documents:commit?key=<KEY>
{ "writes": [{
    "transform": {
      "document": ".../transfer_counters/calib",
      "fieldTransforms": [{ "fieldPath": "n", "increment": { "integerValue": "1" } }]
    }}]}
```

**応答の `transformResults` に、増やしたあとの値が入って返る。**
だから読み出しを許さなくても自分の番号が分かる。あとは現行と同じ規則で
`group = groups[n % 2]`、`assign_index = floor(n / 2)` を出す。

increment はサーバ側で不可分に処理されるので、同時に来ても番号は衝突しない。
**トランザクションを組む必要がない**のがこの方式の利点である。
ルール側で「`n` が 1 だけ増える更新」に限っているので、番号を飛ばしたり
巻き戻したりもできない。

### 3.3 回答の保存

`transfer_trials` に1問1ドキュメント、`transfer_wellbeing` に1参加者1ドキュメント。
どちらも **create だけ許可、read/update/delete は禁止**。
最低限の列が入っているかもルールで見る（形の決まらない書き込みで荒らされないため）。

### 3.4 GAS はどうするか

**当面は二重書き込みで残す**（保険）。ただし**必須依存にはしない**——
GAS への送信が失敗しても実験は続き、Firestore に入っていれば解析できる形にする。
実データで Firestore 側に全件入ることを確認できたら、GAS を落とす。

### 3.5 解析側

`analyze_transfer.py` は「dump JSON / CSV」を読む作りにしてあるので、
**取り出し方が変わっても分析側は変えなくてよい**。Firestore からの取り出しは
`gcloud firestore export` か REST の `runQuery` で JSON にし、同じ列名に直して渡す。

## 4. いま人がやる必要があること（自動化できない部分）

**Firebase プロジェクトがまだ無い。** `experiment/prod_common.js` の `FIREBASE` は
空のままで、iFont 用のプロジェクトは作られていない。

### 既存プロジェクトの流用可否 — 調べた結果「勧めない」

| 候補 | 判断 |
|---|---|
| Kikiwake（`kikiwake-c2e8e`） | **流用しない。** 別の研究が動いている本番プロジェクトで、ルールが「ログイン済みの本人だけ」を前提に組んである。転写検証はログインしない設計なので、ルールを緩める改修が要る。動いている研究のルールに手を入れるのは危ない |
| 実験1用 | **存在しない。** `docs/FIREBASE_SETUP.md` に「作る」と書いてあるだけで未作成 |

→ **転写検証用に新しいプロジェクトを1つ作る**のが最も安全で、手順も短い。

### 手順（Firebase コンソールでの作業・10分ほど）

1. https://console.firebase.google.com/ → **プロジェクトを追加**。名前は `ifont-transfer` など。
   Google Analytics は不要。
2. **構築 → Firestore Database → データベースを作成** →
   **本番モード** ／ ロケーション **asia-northeast1**。
3. **ルール**タブを開き、`firebase/firestore.transfer.rules` の中身を貼って**公開**。
4. **プロジェクトの設定（歯車）→ 全般** で次の2つを控える。
   - プロジェクトID（例 `ifont-transfer`）
   - ウェブAPIキー（`AIza…`）
5. 上の2つを丸山（またはこの作業を続ける担当）に渡す。

> **APIキーの公開について**: Firebase のウェブAPIキーは、設計上クライアントに
> 埋め込んで公開するものである。守るのはキーではなく**ルール**で、
> 上のルールは「作るだけ・読めない・消せない」に絞ってある。
> したがってリポジトリにコミットしてよい。
> （GAS の `DUMP_TOKEN` のような「本来秘密であるべき値」とは性質が違う。）

### 手順（コード側・キーが揃ってから・2〜3時間）

6. `transfer_config.js` に `firestore: { project_id, api_key, enabled }` を追加。
7. `transfer.js` に、3.1〜3.3 の書き込みを実装。**設定フラグで GAS と切り替えられる形**にし、
   フラグを倒せば現行の GAS 構成にすぐ戻せるようにする。
8. 疎通と負荷の確認: 複数IDで連続アクセスし、
   ①番号が飛ばない・重複しない ②重複拒否が効く ③回答が全件入る、を実証する。

## 5. 日程の判断（2026-08-21 時点の推奨）

> **下見は GAS ＋ 再試行のまま出すことを勧める。Firestore 移行は下見のあと。**

理由。

- **今日の failure は再試行で塞がった。** 実機で起きたのは一過性の失敗で、
  3回作り直す実装と「もう一度試す」ボタンで、参加者を取りこぼす経路は無くなった。
  ローカルで障害を再現して確認済み（HTMLが返る状況→3回試して失敗→ボタンで復帰）。
- **Firestore はまだプロジェクトすら無い。** 4章のとおり、人の手作業が先に要る。
  キーが揃うまでコード側は書いても試せない。
- **下見の目的は運用の確認**である。16人で「掲載→回答→完了コード→回収」が回るかを
  見るのが主眼で、保存基盤が GAS か Firestore かは目的に関わらない。
- **未検証の採番機構を、有償の参加者募集の直前に入れるのは割に合わない。**
  採番と重複チェックは間違えると取り返しがつかない（番号の重複・誤ったお断り）。
  下見で GAS を回している裏で作り、本番（較正・検証フェーズ）から使うのが安全である。

**撤退線の扱い**: 8/22 昼の時点で Firestore が完成していなくても、
現行構成は**そのまま下見に出せる状態を保ってある**。今回の変更は再試行の追加だけで、
GAS 側にも設定にも壊れる変更を入れていない。

## 6. この移行が終わったときの状態

- 参加者のブラウザ → Firestore（直）。中継が無いので一過性の失敗が起きにくい。
- 採番は increment 変換で衝突しない。重複チェックは create の成否で判定。
- 読み出しは全面禁止。参加者は他人のデータを見られない。
- GAS は保険として残すか、実データで確認できしだい落とす。
- 実験1（68かな・220人規模）はこの上で回す。
